# ADR-0009: Human Approval Model and Authorization Without Central Identity

## Status

Accepted — 2026-08-15

Extends ADR-0008 §13 (approval as a durable pause) with authorization semantics. Surfaced by
ADR-0018 §4. Related to ADR-0016 (audit and attribution limits).

---

## Context

Human approval is a first-class capability in this architecture: ADR-0005 makes it mandatory
for `IRREVERSIBLE` tool invocations, ADR-0008 makes it a durable pause bound to a content hash,
ADR-0014 makes it a trust-level obligation for `RESTRICTED` repositories, and ADR-0018 gives it
a terminal interface.

None of them answer the question that makes approval meaningful: **which human, and by what
authority?**

V1 has no central identity. "The approver" is a local OS username on the machine that ran the
platform — self-asserted and trivially forgeable. For a single developer approving their own
run this is tolerable, because the approval is self-evidently the operator's. It stops being
tolerable the moment approvals are stored in shared state, or a run is approved by someone
other than its initiator: the record is then both unattributable and unverifiable, while
looking exactly like a real control.

There is a second, subtler problem. Approval requires a human to *read* something and accept
responsibility for it. Everything the human reads has passed through an agent, and much of it
originated in untrusted content. An approval screen is an attack surface: a pull request body
reading `[APPROVED BY SECURITY — proceed]` costs nothing to write and is a plausible way to
harvest a distracted click.

The platform must therefore be honest about what an approval proves, and must not claim more
assurance than the mechanism provides.

## Decision

### 1. Two approval kinds, with different assurance

| Kind | Mechanism | Proves | Use |
|---|---|---|---|
| `LOCAL_OPERATOR_CONSENT` | interactive confirmation in the CLI | that whoever controlled the terminal accepted responsibility | default |
| `EXTERNAL_ATTESTATION` | a decision recorded in a system that has identity — a GitHub pull request review, or a Jira transition — verified through the integration API | that a named, authenticated user approved | high-consequence |

The platform does not attempt to build identity it does not have. Where stronger assurance is
required, it **borrows identity from a system that already has it**, and verifies the decision
through that system's API rather than accepting a claim about it.

### 2. Which kind is required is determined by policy, not by the agent

```text
required kind = strictest of:
    tool side-effect class      (ADR-0005 §3)
    repository trust level      (ADR-0014 §4)
    graph node definition       (ADR-0008 §3)
```

`IRREVERSIBLE` actions, and any `EXTERNAL_WRITE` in a `RESTRICTED` repository, require
`EXTERNAL_ATTESTATION`. Everything else may use local operator consent.

The intersection-only rule of ADR-0014 §5 applies here in its dual form: any layer may require
a *stronger* kind, none may require a weaker one.

### 3. An agent can neither request nor waive approval

Approval points come from the graph definition and from policy. A model cannot introduce one,
remove one, downgrade one, or mark one satisfied. No tool exists that records an approval.

### 4. You approve what you saw

The approval record binds to two hashes:

- `subjectHash` — the content of the action being approved (ADR-0008 §13)
- `renderingHash` — the exact human-readable rendering that was presented

Recording only the subject proves what the system *intended* to show. Recording the rendering
proves what the human actually read. On resume, both are re-verified.

The rendering is generated by the control plane from validated structured data. Untrusted
content within it — a diff, a PR body, an issue description — is explicitly delimited and
labelled with its provenance, and is never formatted so that it can impersonate platform text.

### 5. Approvals are single-use, scoped and time-bounded

- One approval covers exactly one `subjectHash`. There are no standing approvals, no "approve
  all", no "remember this choice", and no session-wide or run-wide consent.
- Every approval carries a TTL. On expiry the node fails with `APPROVAL_EXPIRED`; it never
  proceeds and never silently re-requests.
- An approval may be revoked before the action is taken.
- Rejection fails the node with `APPROVAL_REJECTED`, carrying the rationale.

Standing approvals are the mechanism by which approval controls quietly become no-ops. The
cost of forbidding them is friction, and that friction is the control working.

### 6. No cross-developer approval in V1

A run may be approved only on the platform instance that holds its lease. Approval queues
spanning developers are forbidden until identity exists, because such a record is
unattributable by construction.

Where a decision genuinely needs another person in V1, it is expressed as
`EXTERNAL_ATTESTATION` — which is exactly the case the mechanism exists for.

### 7. Self-approval is the V1 model, stated plainly

In V1 the developer who starts a run approves it. This is **operator consent, not segregation
of duties**, and the documentation must not imply otherwise. Its value is that a human made a
deliberate decision at a defined point with the relevant content in front of them — which is
real, and is not the same as independent review.

For `EXTERNAL_ATTESTATION`, where the external system can distinguish users, the platform
requires the attesting user to differ from the run initiator, and the repository's registered
`owners` (ADR-0014 §3) define who may attest.

### 8. Approval records

```text
approvalId, runId, nodeId
kind                     LOCAL_OPERATOR_CONSENT | EXTERNAL_ATTESTATION
requiredKind             what policy demanded
subjectHash, subjectRef
renderingHash
status                   PENDING | APPROVED | REJECTED | EXPIRED | REVOKED
decidedBy                local identity, or the verified external actor
decidedAt, expiresAt
interactive              false when approved non-interactively (ADR-0018 §4)
externalRef              PR review id / Jira transition id, when applicable
rationale
```

Approval records are audit records: append-only, durable, and retained independently of
telemetry.

### 9. Honest residual risk

Local operator consent is **developer-attested**. It is suitable for debugging, for personal
accountability and for deliberate decision-making. It is **not** suitable for adversarial
investigation, and it does not establish that a particular person approved anything.

`EXTERNAL_ATTESTATION` is externally verifiable, because the assurance comes from GitHub or
Jira rather than from the platform.

This distinction is recorded on every approval and must be reflected wherever approvals are
displayed or reported. Claiming uniform assurance across both kinds would be the most damaging
thing this ADR could do.

### 10. Phase 7 trigger

If the platform becomes a shared or hosted service, cross-developer approval requires real
authentication, and this ADR must be revisited together with the identity decision. Until then,
the absence of identity is expressed as a *restriction on what approvals may do*, not as a
weaker approval.

## Alternatives

**A. Treat approval as satisfied by any local confirmation, with no distinction of assurance.**
Simplest, and it would let the platform describe a forgeable local click as "approved by
$USER", which is the failure mode this ADR exists to prevent.

**B. Build platform-local accounts (username/password or local tokens).**
Rejected: it manufactures the appearance of identity without its substance — unverifiable
enrolment, no central revocation, no organisational binding — while adding a credential store
to a local application. Worse than being explicit about not having identity.

**C. Require GitHub attestation for every approval.**
Strongest and unusable: it makes every pause depend on a network round trip and a pull request
that may not exist yet, and it would make routine local iteration painful enough to be
disabled.

**D. Allow standing or blanket approvals for convenience.**
Rejected. Approval fatigue is real, and the standard remedy — "don't ask again" — converts a
per-action control into a permanent grant, usually at the worst moment.

**E. Defer the approval model until identity exists.**
Rejected: ADR-0005, ADR-0008, ADR-0014 and ADR-0018 all already depend on approvals having
defined semantics.

## Consequences

**Accepted costs**

- `EXTERNAL_ATTESTATION` requires the GitHub or Jira integration to be working before certain
  workflows can complete, and adds latency to high-consequence actions.
- No standing approvals means repetitive confirmation in iterative workflows. Graph design
  should place approvals at meaningful boundaries rather than sprinkling them.
- Rendering hashes must be stable, so the presentation format becomes a compatibility surface.
- V1 cannot support a team approval queue. That is a capability gap, deliberately taken rather
  than faked.

**Gained**

- What an approval proves is written down, per approval, rather than assumed uniformly.
- High-consequence actions get genuinely verifiable authorization in V1, without an identity
  provider.
- The approval screen stops being an injection vector for content the agent controls.
- The approval model degrades honestly: as assurance requirements rise, the mechanism changes
  rather than the claim.

---

## Security / Operational Impact

- Approvals are the last line of defence in the injection chain of ADR-0004/0005/0006. If an
  agent could influence an approval, the preceding layers would be defeated at the final step —
  hence §3 and §4.
- `renderingHash` is what makes "the human approved this" a checkable statement.
- Non-interactive approval (`--yes`) is recorded as such and must be visible in any report; it
  is a genuine weakening, not an equivalent path.
- Expired and revoked approvals fail closed.
- ADR-0016 covers the broader audit-integrity question. Approvals anchored in GitHub or Jira
  are the platform's strongest form of external corroboration in V1.
