# ADR-0024: Contract Source of Truth, Code Generation and Schema Versioning

## Status

Accepted — 2026-08-15

Establishes the mechanism by which the Java control plane (ADR-0004) and the Python agent runtime
share one contract definition. Depends on ADR-0019 for type names and ADR-0020 for serialisation
rules. Required by the M2 exit criteria in `ROADMAP.md`.

---

## Context

The platform is deliberately two languages: a Quarkus control plane and a Python agent runtime,
separated by an HTTP protocol (ADR-0004 §11). They exchange `AgentExecutionRequest`,
`AgentExecutionResult`, `ToolRequest`, `ToolResult`, `ContextBundle`, `ModelRequest` and
`ModelResponse`, and they must agree on all of them exactly.

Today `schemas/` holds 21 JSON Schemas that nothing consumes. They are validated by
`schemalint` and are otherwise documentation. The moment implementation starts, the default
outcome is well known: someone writes Java records by hand, someone else writes Python
dataclasses by hand, and both drift from the schemas and from each other. The drift is silent,
because each language's tests pass against its own model.

The failure mode this produces is specific. A field that is required in the schema but optional
in the Python model, or an enum value present in Java and missing in Python, does not fail at
build time. It fails when the control plane sends a message the runtime cannot parse — at a node
boundary, mid-run, in a system whose whole purpose is durable long-running workflows.

Three things must be decided together, because each constrains the others: which artifact is
authoritative, how the other artifacts are produced, and what happens when the authoritative one
changes.

---

## Decision

### 1. The JSON Schemas are the single source of truth

`schemas/**/*.schema.json` is the canonical definition of every contract. Nothing else is
authoritative — not the generated Java, not the generated Python, not the prose in
`docs/contracts/`, not a database DDL.

A contract change is a schema change. Hand-written contract types in either language are
prohibited, and CI enforces it by regenerating and diffing.

The prose specification remains valuable for what a schema cannot express — invariants, state
machines, rationale — and remains subordinate: where the two disagree, the schema is correct and
the prose is a defect.

### 2. Both languages are generated by one generator

```text
schemas/**/*.schema.json
        │
        └── .github/scripts/codegen.py
                    ├── contracts/java/   Java 17 records, enums, sealed interfaces
                    └── contracts/python/ dataclasses with explicit (de)serialisation
```

A single generator, rather than a per-language tool, is the load-bearing choice. Two independent
generators would have to be *shown* to interpret `required`, `additionalProperties`, `oneOf` and
`x-hashExclude` identically; one generator interprets each construct once, and any divergence is
a bug in one place rather than a disagreement between two vendors' interpretations of a
specification.

The generator is Python, standard library only, matching `doclint.py` and `schemalint.py`. It
introduces no dependency into either target language's build, and it runs anywhere Python 3.12
does — including a laptop with no network, which ADR-0001 requires.

Existing tools were considered and rejected in Alternatives; the decisive factor is that the
schema set uses draft 2020-12 with cross-file `$ref`s, discriminated `oneOf` unions and a custom
`x-hashExclude` annotation, and no off-the-shelf tool handles that combination in both languages.

### 3. Generated code is committed, and CI verifies it regenerates identically

Option A of the two available policies:

```text
CI:  regenerate → git diff --exit-code → fail if anything changed
```

Committing generated code is chosen for reasons specific to this repository:

- **Review sees the blast radius.** Changing `required` in a schema is a two-character diff whose
  consequences appear in the generated types. A reviewer should see that a field became mandatory
  in eleven places.
- **No build-time dependency.** Neither Maven nor a Python build needs to invoke Python codegen,
  which keeps `contracts/java` a plain Maven module and `contracts/python` a plain package.
- **It matches the repository's existing philosophy.** Every check here is a drift check —
  doclint, schemalint, the invalid-example suite. "Regenerate and diff" is the same idea applied
  to code.
- **The failure is loud and early.** A contributor who edits a schema and forgets to regenerate
  fails CI in seconds with an obvious message, rather than shipping a mismatch.

The cost — generated code in diffs — is real and accepted. It is mitigated by keeping generated
files under two clearly named directories that `CODEOWNERS` marks and that reviewers can collapse.

Every generated file carries a header naming the generator and the source schema, and states that
edits will be overwritten.

### 4. Generated models carry no behaviour

Generated types are data carriers: fields, constructors, equality, and explicit conversion to and
from JSON-compatible structures. They contain no validation logic, no business rules and no
convenience methods.

Validation is performed against the JSON Schema itself, by a schema validator, not by
hand-maintained checks embedded in a generated class. Two reasons: a generated validator would be
a second, weaker implementation of a specification that already has a validator; and constraints
that JSON Schema expresses easily — `pattern`, `uniqueItems`, conditional `required` — are exactly
the ones that generated per-language validation gets wrong.

Consequently a generated type can hold an invalid document. That is intentional: parsing and
validation are separate steps, and conflating them is what leads to models that are validated in
one language and not the other.

Per ADR-0020 §3, both languages omit absent optional fields on serialisation and never emit
`null`.

### 4a. How `oneOf` and open objects are represented in generated code

JSON Schema can express shapes that neither Java records nor Python dataclasses have a direct
equivalent for. The generator's handling of these is part of the contract, not an implementation
detail, because both languages must land on the same representation or the conformance test
compares two different models.

**Discriminated unions become one flattened record.** Where a `oneOf` lists object branches, the
generated type is a single record whose fields are the union of every branch's fields, with fields
absent from some branch made optional. String `enum` and `const` values for the same property name
are unioned across branches rather than taken from the first branch.

This last rule is load-bearing and was got wrong once. Taking the discriminator from the first
matching branch silently produces an enum missing every other branch's value — a generated type
that compiles, round-trips most documents, and rejects valid ones. Validation remains the schema's
job; the generated record is a carrier, and per §4 it does not enforce which combination of fields
is legal.

**Heterogeneous unions become freeform.** Where a `oneOf` mixes an object branch with a scalar
branch — `ModelRequest.toolChoice` is `"AUTO"` or `{"name": ...}` — no record can carry both, so
the generated type is `Object` in Java and `Any` in Python.

**Objects that declare properties *and* allow additional ones become freeform.** `Tool.inputSchema`
declares known fields with `additionalProperties: true`. Generating a record for it would silently
drop every undeclared key on round trip, which is data loss disguised as a type. The generated type
is a map.

**Self-referential definitions are emitted once, by name.** A `$ref` that re-enters a definition
already being generated — `Condition` refers to itself through `expression` — resolves to a
reference to the in-progress type rather than expanding it, which would not terminate.

Each of these is a deliberate loss of static typing in exchange for not losing data. Where the
generator cannot represent a shape faithfully, it produces a permissive type rather than a precise
type that is wrong.

### 5. `schemaVersion` is a single integer-valued string per document kind

Stored documents carry `schemaVersion`; wire protocol messages carry `protocolVersion`
(ADR-0004 §11). The distinction mirrors ADR-0019 §3: entities are stored and versioned as data,
protocol messages are exchanged and versioned as a conversation.

Both are `const` strings, currently `"1"` everywhere. There is exactly one version of every
contract in V1, and no migration machinery exists.

### 6. Compatibility rules

| Change | Compatible | Requires a version bump |
|---|---|---|
| Add an optional field | ✅ | |
| Add documentation or a description | ✅ | |
| Relax a constraint (widen a pattern, raise a maximum) | ✅ | |
| Add a **required** field | | ✅ |
| Remove or rename any field | | ✅ |
| Narrow a constraint | | ✅ |
| Change a type | | ✅ |
| **Add an enum value** | | ✅ |
| **Remove an enum value** | | ✅ |

Adding an enum value is breaking. This is stricter than common practice and is chosen
deliberately: generated enums are closed in both languages, so a recipient that has not been
regenerated fails to parse the new value. The alternative — an `UNKNOWN` fallback member — makes
every consumer silently tolerant of values it does not understand, which for `sideEffectClass`,
`failureCategory` or `trustClass` means treating an unrecognised security-relevant value as
benign. Failing to parse is the correct behaviour for this platform, and it matches the
fail-fast-at-startup posture ADR-0004 already takes for `protocolVersion`.

A version bump requires an ADR when the affected document is persisted, because existing stored
documents then need a migration plan, and V1 has no migration framework.

### 7. Java and Python are only ever compatible at the same commit

The two languages are generated from one schema set in one repository and are expected to be
deployed together. V1 promises no compatibility between a control plane and an agent runtime built
from different commits.

`protocolVersion` makes the mismatch fail fast at startup rather than at the first interesting
node (ADR-0004 §11), which is the guarantee that actually matters locally: a developer running a
stale runtime learns immediately.

Independent deployment and rolling upgrades are a hosted-deployment concern, coupled to the
identity question deferred in ADR-0002, and are not V1 problems.

## Alternatives Considered

**`jsonschema2pojo` for Java and `datamodel-code-generator` for Python.** The obvious choice, and
rejected on three counts. Neither fully supports draft 2020-12 with the cross-file `$ref`s and
discriminated `oneOf` unions the schema set uses; they would interpret `required`,
`additionalProperties` and union discrimination independently, so equality of the two models
becomes an empirical question rather than a structural one; and both add a build-time dependency
and a network fetch to a platform whose first principle is that it runs on a laptop. Bespoke
generation is more code here but far less risk, because the schema subset in use is small and
fixed.

**Hand-write models in both languages, with schema validation in tests.** Rejected. It is the
default outcome this decision exists to prevent. Tests would catch a mismatch only where someone
thought to write one, and the cross-language cases are precisely the ones nobody writes.

**Define contracts in an IDL — Protocol Buffers, Smithy, OpenAPI — and generate JSON Schema from
it.** A defensible architecture, and rejected because the repository already has 21 reviewed,
ADR-linked JSON Schemas with an example suite and a lint. Migrating to an IDL would discard that
work, add a toolchain, and make the contracts less readable in review. OpenAPI in particular
describes endpoints; most of what needs sharing here is stored entities, not endpoints.

**Option B: generate at build time, commit nothing.** Rejected. It hides the blast radius of a
schema change from review, forces both language builds to depend on the Python generator, and
converts an obvious `git diff` failure into a subtler build-ordering problem.

**Tolerant enums with an `UNKNOWN` member.** Rejected for the reason in §6: silent tolerance of
unrecognised security-relevant values.

## Consequences

- `contracts/java/` and `contracts/python/` are added, containing generated code only.
- `.github/scripts/codegen.py` becomes a maintained component: a new JSON Schema construct is
  only usable once the generator supports it. This is a real constraint and a deliberate one — it
  keeps the schema set within a subset that is expressible in both languages.
- CI gains a regeneration-and-diff check, a Java compile, and a Python import check.
- Contributors must run the generator after editing a schema. `CONTRIBUTING.md` documents it.
- Adding an enum value is a breaking change, so failure categories, side-effect classes and
  status enums must be considered carefully before publication rather than extended casually.
- Generated types cannot enforce invariants, so the invariant traceability in
  `docs/contracts/v1-domain-contracts.md` remains the record of where enforcement lives.
- A third language, if ever needed, is a generator backend rather than a new contract definition.

---

## Security / Operational Impact

Contract drift between the control plane and the agent runtime is a security concern, not only a
correctness one. The boundary carries the security-relevant fields of the platform:
`callbackToken`, `sideEffectClass`, `trustClass`, `capabilityGrant` subjects and
`approvalPolicy`. A field that is required on one side and optional on the other is precisely how
a control becomes unenforced in practice — the sender stops populating it, the receiver stops
requiring it, and nothing fails.

Generation from one source removes the class of defect. The regeneration diff makes any attempt to
weaken a contract in one language only visible in review.

Closed enums support this: an agent runtime that receives an unrecognised `sideEffectClass` fails
rather than defaulting, and a default at that position would default toward permission.

Generated code executes nothing and reaches nothing. The generator runs offline over files in the
repository, with no network and no credentials.
