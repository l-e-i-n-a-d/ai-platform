# Approvals

**Status:** Planned (design agreed, not yet implemented)
**Location:** Control plane; surfaced through the CLI
**Decisions:** [ADR-0009](../decisions/0009-human-approval-model.md),
[ADR-0008 §13](../decisions/0008-graph-execution-semantics-and-durability.md)

---

## 1. Flow

```text
graph reaches an approval point
        |
        v
control plane writes AWAITING_APPROVAL, RELEASES THE LEASE, stops
        |
        v
aip run list  ->  pending approval
        |
        v
aip run approve <id>
   renders the subject + shows subjectHash and renderingHash
   requires interactive confirmation
        |
        v
decision recorded (append-only)  ->  aip run resume  ->  graph continues
```

Nothing is held in memory across the pause. A run may wait for days; the laptop may be closed
and reopened.

---

## 2. Two kinds

| Kind | Mechanism | Proves |
|---|---|---|
| `LOCAL_OPERATOR_CONSENT` | interactive CLI confirmation | whoever controlled the terminal accepted responsibility |
| `EXTERNAL_ATTESTATION` | GitHub PR review or Jira transition, verified via the API | a named, authenticated user approved |

The required kind is the **strictest** of the tool's side-effect class, the repository's trust
level and the graph node definition. Any layer may require a stronger kind; none may require a
weaker one.

`IRREVERSIBLE` actions, and `EXTERNAL_WRITE` in a `RESTRICTED` repository, require
`EXTERNAL_ATTESTATION`.

---

## 3. Binding

Two hashes are recorded:

- `subjectHash` — what is being approved
- `renderingHash` — the exact text the human was shown

The first proves what the system intended to present; the second proves what was actually read.
Both are re-verified on resume; a change to either voids the approval.

The rendering is generated by the control plane from validated structured data. Untrusted
content inside it is delimited and labelled with provenance, and can never impersonate platform
text. An approval screen an agent can influence would defeat every preceding control.

---

## 4. Rules

- one approval covers exactly one `subjectHash` — no standing, blanket or run-wide approvals
- every approval has a TTL; expiry fails the node with `APPROVAL_EXPIRED` and never re-requests
  silently
- rejection fails the node with `APPROVAL_REJECTED` and a rationale
- approvals may be revoked before the action is taken
- expired and revoked approvals fail closed
- no agent may request, waive, downgrade or record an approval
- approvals may only be given on the platform instance holding the run's lease — no
  cross-developer queues in V1

---

## 5. What V1 approval proves

`LOCAL_OPERATOR_CONSENT` is **developer-attested**: a human made a deliberate decision at a
defined point with the content in front of them. It is operator consent, **not segregation of
duties**, and it is not evidence for adversarial investigation.

`EXTERNAL_ATTESTATION` is externally verifiable, because the assurance comes from GitHub or
Jira rather than from the platform. Where the external system can distinguish users, the
attester must differ from the run initiator, and the repository's registered `owners` define
who may attest.

Every approval records which kind it was, and whether it was given interactively. Reports must
never present the two kinds as equivalent.

---

## 6. Record

```text
approvalId, runId, nodeId
kind, requiredKind
subjectHash, subjectRef, renderingHash
status        PENDING | APPROVED | REJECTED | EXPIRED | REVOKED
decidedBy, decidedAt, expiresAt
interactive
externalRef
rationale
```

Append-only, durable, retained independently of telemetry.
